# Вход через Яндекс, Telegram и почту

## Что исправлено

В Яндекс OAuth state-cookie раньше выставлялась на текущем домене, но callback всегда шёл на `NEXT_PUBLIC_SITE_URL` / `SITE_URL`. При открытии через `www`, другой домен или preview браузер не передавал host-only cookie на callback, и сайт возвращал общую ошибку. Теперь переход на настроенный домен выполняется **до** создания cookie и отправки в Яндекс. Cookie остаётся httpOnly / SameSite=Lax / Secure на HTTPS; проверка state не ослаблена. Host запроса учитывается отдельно от внутреннего HTTP/localhost-адреса reverse proxy.

Это воспроизводимый дефект кода, но не доказательство причины любого production-сбоя. По одной общей ошибке старой версии нельзя отличить потерянную cookie от ошибки провайдера, БД или сессии. Белый экран/долгая загрузка на самом `oauth.yandex.ru` также не доказывает ошибку callback сайта.

Дополнительно:

- OAuth-редиректы запрещено кешировать; Referrer-Policy не передаёт callback URL с кодом на последующие страницы.
- Ответы Яндекса проверяются до использования access token / профиля. Запросы ограничены таймаутом; сбой сети, код входа, профиль, БД и сессия различаются.
- Создание имени использует больший случайный суффикс; конкурентное создание одного email переиспользует созданный аккаунт. Существующая роль, пароль и право редактора при входе не меняются.
- Незавершённая миграция БД теперь даёт отдельную причину `schema` и HTTP 503 при входе по почте/Telegram, а не маскируется общей ошибкой.
- При отсутствующем/коротком `SESSION_SECRET` выдаётся понятная ошибка, без ослабления защиты. Блокировки и отзыв сессий продолжают действовать.
- Ошибка остаётся внутри формы входа после исчезновения toast. Server log OAuth содержит только requestId, этап, безопасную категорию и SQLSTATE — без кодов авторизации, токенов, SQL, email и секретов.

## Проверка рабочего сайта

1. **База данных.** В SQL Editor того же Supabase-проекта, который использует приложение, выполнить `scripts/supabase/04-auth-check.sql`. Это read-only проверка наличия/типов 11 колонок аккаунтов, без чтения пользовательских данных. Если есть `MISSING` / `WRONG_TYPE`, сначала backup и целиком `01-upgrade.sql`, затем `02-verify.sql` + `03-schema-audit.sql`. Если всё `OK`, это не исключает других проблем доступа/подключения — полный audit и логи проверяются отдельно.
2. **Канонический адрес.** На сервере настроить `SITE_URL=https://moviemovie.ru` (или фактический основной HTTPS-домен). Серверный `SITE_URL` приоритетнее устаревшего `NEXT_PUBLIC_SITE_URL`. Если используется только публичная переменная, она должна содержать тот же адрес. Без пути, query и fragment. Локальный HTTP допустим только вне production. Изменения окружения требуют redeploy / перезапуска.
3. **Яндекс OAuth.** Redirect URI в настройках приложения должен **в точности** совпадать с `https://moviemovie.ru/api/oauth/yandex` (с учётом фактического домена), разрешения — `login:email` и `login:info`. Проверить наличие `YANDEX_CLIENT_ID` и `YANDEX_CLIENT_SECRET` в production-окружении того же приложения. Не присылать значения в чат. При открытии входа с `www` сначала должен произойти переход на основной домен, затем в Яндекс.
4. **Сессии.** Проверить наличие `SESSION_SECRET` длиной не менее 32 символов. Если он уже задан правильно, не менять без необходимости: ротация завершает все существующие сессии.
5. **Telegram.** Проверить `TELEGRAM_BOT_TOKEN`, build-time `NEXT_PUBLIC_TELEGRAM_BOT_NAME` и домен Login Widget у бота. Сервер проверяет подпись и свежесть payload. Токен бота никогда не помещается в `NEXT_PUBLIC_*`.
6. Повторить вход в обычной вкладке с разрешёнными cookie. Проверить почту и пароль отдельно от Яндекса. Для поддержки достаточно категории `?auth=...`, результата проверки колонок и безопасной строки `[OAUTH] Login failed`; полный callback URL с `code`/`state` публиковать не нужно.

Новые причины callback: `state`, `token`, `profile`, `unavailable`, `schema`, `database`, `session`, `blocked`, `config`, `cancelled`. Пользователь видит локализованное объяснение, неизвестные значения не отражаются как HTML/текст из URL.

## Автотесты

`npm run test:auth` запускает реальные OAuth/auth/session реализации с временной PGlite. Подменяются только HTTP Яндекса и request-cookie context Next: полный happy path с созданием и повторным входом, связка по email, подписанная сессия, www/preview/proxy, CSRF/отмена, невалидный token/profile, сеть/5xx, отсутствие миграции/SESSION_SECRET, блокировка/отзыв сессии, пароль и корректно подписанный Telegram. Реальный внешний OAuth и конфигурация production при этом не проверяются.

`npm test` включает unit-проверки конфигурации адреса, безопасных ошибок и прежние проверки авторизации/ролей. Production HTTP/browser smoke проверяет реальную cookie-сессию и отображение формы отдельно. Секреты и рабочая БД для локальных тестов не нужны.

Новая SQL-миграция для этого исправления **не требуется**: `04-auth-check.sql` только диагностирует уже существующую схему. Недостающие миграции предыдущего обновления всё равно необходимо применить. Никакие миграции/настройки рабочего проекта автоматически не меняются.
