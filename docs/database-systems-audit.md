# MovieMovie: проверка БД по всем текущим системам

Дата: 22 ноября 2026. Проверены исходники схемы, API и миграции текущей версии.
**Это не отчёт о фактическом состоянии рабочей Supabase:** подключения к ней в этой
сессии не было. Её состояние показывает поставляемый read-only SQL-аудит.

## Итог

Текущему коду нужны **31 таблица, 214 столбцов**, а также индексы и ограничения из
Drizzle-схемы. Семь предыдущих миграций покрывают функциональные изменения этой
серии задач. Добавлена **восьмая миграция индексов**, полная структурная проверка
и автоматический контроль перед фиксацией SQL-пакета. Новых сущностей ради
ещё не реализованных идей не создаём.

| Система | Где данные | Что нужно в БД / решение |
|---|---|---|
| Регистрация, профиль, OAuth, Telegram, роли | `mg_users` | Существующие поля; сессия подписана cookie, отдельной таблицы сессий сейчас нет |
| Каталог, поиск, категории, главная, топ материалов | `mg_movies`, `mg_ratings`, `mg_watches` | `cast`, `franchise`, `festival_recognized` добавляются прежними миграциями; новые индексы просмотров/оценок |
| Оценки и распределение рейтинга | `mg_ratings` | Уникальность user/movie, расчёт среднего из голосов; отдельный кэш рейтинга не нужен |
| Просмотры, история, статистика, недельный топ | `mg_watches`, `mg_users` | Индексы user/movie, user/date и movie; недельный топ вычисляется, таблица «победителей» не нужна |
| Статистика посещений карточек | `mg_movies.views`, cookie | Новая таблица не нужна; cookie-антидубль не является строгой антифрод-системой |
| Закладки и избранное | `mg_bookmarks`, `mg_favorites` | Существующие таблицы и уникальные пары |
| Комментарии, ветки, спойлеры, реакции | `mg_comments`, `mg_reactions` | Поле spoiler есть в миграциях, parent_id/edited_at — базовая схема; индекс movie/date |
| Друзья и сравнение вкусов | `mg_friendships`, оценки/просмотры | Существующие данные; полноценный поиск кино-двойников пока план, отдельной таблицы нет |
| Уведомления и личные сообщения | `mg_notifications`, `mg_messages` | Индексы user/date и from/to/date; данные/политики существующих таблиц не переписываются |
| Совместные списки и кинокомнаты | `mg_collab_lists`, `mg_collab_items`, `mg_watch_rooms` | Существующая схема; новая групповая рулетка ещё не выпущена |
| Киноклуб | `mg_movie_club` | Существующая таблица |
| Ежемесячные задания и награды | `mg_challenges`, `mg_challenge_progress` | Существующие поля progress/completed/reward_claimed; таблица не заменяется |
| Мини-игры | `mg_game_scores` | Существующая таблица для результатов |
| Вопрос дня на главной | каталог + localStorage | Прогресс локален браузеру и не даёт наград; синхронизация между устройствами пока не реализована |
| Достижения, постоянные титулы | журналы `mg_hidden_achievement_*`, `mg_user_title_awards`, users.equipped_title | Есть в прежних миграциях, с RLS и закрытием браузерных ролей |
| Полные сезоны/эпизоды, отдельные оценки | `mg_series_seasons`, `mg_series_episodes`, `mg_season_ratings`, `mg_episode_ratings` | Пятая миграция, уникальные номера, диапазоны оценок, реальные данные вводит редактор |
| Серийные завершения и «Первопроходец» | `mg_series_completions`, `mg_movie_pioneers`, movies.series_catalog_complete | Пятая миграция; заслуженное не пересчитывается как временное состояние |
| Питомец | `mg_cinema_pets` | Шестая миграция: развитие, покупки, настройки и приватность |
| Кошелёк, idle, дневные/недельные задания, рубежи | `mg_popcorn_ledger`, `mg_cinema_pets` | Шестая/седьмая миграции, постоянные source keys; восьмая добавляет индекс истории |

| Загрузка аватаров/постеров/обложек | Supabase Storage `uploads`, URL в users/movies | Отдельный необязательный `04-storage-setup.sql`; это не миграция обычных таблиц |

## Что применять

1. Сделать backup рабочей БД; прогнать на staging.
2. В Supabase SQL Editor выполнить **весь** `scripts/supabase/01-upgrade.sql`.
   В пакете девять миграций; установленные пропускаются по имени и SHA-256.
   В конце проверяется вся структура, затем COMMIT. Ошибка откатывает пакет.
3. Выполнить `02-verify.sql` и `03-schema-audit.sql`. У всех проверок должен быть **OK**.
4. При использовании стандартной загрузки — отдельно `04-storage-setup.sql`.
5. Только затем выкладывать приложение.

Если база сильно старее базового состояния проекта, **сначала** выполните
`03-schema-audit.sql`: он безопасно покажет отсутствующие таблицы, столбцы и ключи,
не читая пользователей и тексты. Пакет не является универсальным восстановителем
повреждённых или произвольно изменённых баз. Он не подставляет личные данные и
не меняет типы/содержимое старых колонок автоматически.

## Автоматизация

- `npm run db:bundle` — воспроизводимо собирает единый SQL и аудит из текущей схемы.
- `npm run db:migrate -- --dry-run` — локальный список/хеши, без подключения к БД.
- `npm run db:migrate` — одна транзакция, блокировка, применение недостающего,
  проверка readiness и всей схемы **до COMMIT**.
- `npm run db:verify` — только чтение, отдельная проверка уже работающей БД.
- GitHub Actions **Apply Supabase migrations** — ручной запуск после настройки
  environment `production` и секрета `SUPABASE_DB_URL`; сначала локальные тесты,
  затем миграции/проверка/статус. Обычный git push не меняет БД.

Подключение задаётся в MIGRATION_DATABASE_URL (fallback DATABASE_URL), не в коде.
Подробности и правила таймаутов: [Supabase README](../scripts/supabase/README.md).

## Границы проверки

Контракт сверяет наличие 31 таблицы/214 столбцов, типы и nullability, наличие
обязательных DEFAULT, PK/unique/FK с действиями удаления, валидные индексы с нужными
колонками/уникальностью, именованные валидированные CHECK и требуемый RLS.
Он не доказывает эквивалентность выражений DEFAULT/CHECK, не аудирует все старые
политики RLS и не проверяет корректность наполнения каталога или каждого счётчика.
Новые индексы неуникальные: старые дубли не удаляются и уникальность не меняется.

Локальная интеграционная проверка включает исходную схему, девять миграций и повтор
пакета, намеренное отсутствие поля/таблицы/индекса, неверный тип, отсутствующий default,
выключенный RLS, отказ фиксации при drift, а также Storage-stand-in без реальных файлов.
PGlite не заменяет staging на рабочей версии Supabase и нагрузочные проверки.
