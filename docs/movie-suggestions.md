# Полная предложка и модерация материалов

## Пользовательский сценарий

В каталоге «Предложить кино» открывает тот же редактор полей, что используется кураторами при добавлении материала: название/оригинальное название, описание, категория, годы и ongoing, возраст, минуты/серии, жанры, настроение, студия, режиссёр, страна, актёры, франшиза, фестивальная отметка, ссылка просмотра, постер и фон. Комментарий редакции хранится отдельно от публикуемого описания.

Обязательны название от двух символов, описание, категория, год, корректная длительность и постер. Изображение можно указать ссылкой или загрузить JPEG/PNG/WebP до 4 МБ в настроенный Supabase Storage. Для обычного пользователя добавлены отдельные upload kinds `suggestionPoster`/`suggestionBackdrop`, пути scoped по user ID. Права на curator-only `poster`/`backdrop` не расширялись. Загрузка не публикует материал автоматически. Незавершённые загрузки не имеют автоматического garbage collection; это общая отдельная задача Storage.

Есть предпросмотр и раздел «Мои предложения» со статусами/причиной отказа/ссылкой на публикацию. Обычный пользователь получает из `/api/data` только свои заявки, модераторы — очередь и историю всех заявок, гость — пустой список. Уведомление об отказе ведёт в `/catalog?suggestions=mine` и автоматически открывает форму с историей. История в форме ограничена 20 последними записями для компактности (API возвращает все свои записи).

Форма — native dialog: фокус ограничен диалогом, Escape/закрытие запрашивают подтверждение при изменённых полях. На время отправки/загрузки случайное закрытие блокируется. Ошибка оставляет введённые данные в открытой форме; постоянного draft-хранилища между перезагрузками страницы пока нет.

## Очередь редакции

В админке по умолчанию **только pending**. Принятые и отклонённые не удаляются из БД, а доступны на отдельных вкладках истории. Категория, поиск (название/оригинальное название/автор/год), порядок «старые/новые» пересекаются. Карточка показывает постер, автора, дату, основные метаданные и раскрываемые описание/данные.

«Проверить и одобрить» открывает заполненный редактор. Модератор исправляет поля и нажимает «Одобрить и открыть материал». В **одной транзакции** создаётся фильм, фиксируется решение/ссылка, проверяется награда автору и записывается уведомление. После успеха оболочка перечитывает данные и открывает `/movie/:id`. Отдельно вручную создавать материал больше не нужно.

Если соответствующий материал уже добавлен, доступна кнопка «Уже в каталоге — связать»: проверяется совпадение нормализованного названия, года и категории. Каталог не перезаписывается данными заявки. Старая краткая заявка не теряется: модератор дополняет её в общей форме или связывает с существующим материалом.

Отклонение открывает отдельный native dialog с обязательной причиной до 500 символов. Отмена/Escape ничего не меняют. Автор получает причину в уведомлении и истории; после отклонения можно предложить исправленную карточку заново.

## Серверные гарантии

- Единый allowlist/валидатор `material-input.ts` для прямого добавления, новой заявки и модераторской публикации. Клиент не может прислать owner/status/views/featured/reward как поля фильма.
- Максимум 5 pending от автора: проверка и вставка под блокировкой строки пользователя, в том числе для одновременных запросов.
- Дубли pending и каталога: регистронезависимые title + year + category. Advisory lock общей identity используется предложкой и прямым `movieSave`. При совпадении с существующим фильмом публикация не создаёт дубль, требуется явное связывание.
- Одобрение/отклонение сериализуются блокировками автора и заявки. Повтор одобрения возвращает уже созданный movieId, не создаёт материал/награду/уведомление второй раз; противоречащее решение получает 409.
- Уведомление, награда, фильм и решение откатываются вместе при ошибке. Награда подчиняется прежним дневным лимитам и ledger dedup; клиент не выбирает сумму.
- Полная карточка хранится в nullable JSONB `material`; старые записи остаются `NULL`. Проверка контракта выполняется сервером перед созданием и повторно при публикации.
- RLS и отзыв доступа Data API защищают заявки; приложение использует прежнее серверное PostgreSQL-подключение. SSE ревизии обновляются для автора и всех модераторов без передачи содержания заявки через поток.

## Выкладка — миграция нужна ДО новой версии приложения

Новая миграция: `scripts/migrations/20261122-zzz-full-suggestions.sql` (десятая).
Она добавляет JSONB, два индекса, защиту доступа и trigger ревизий. Старые миграции не редактировались; пользовательские данные не удаляются.

1. Сделать резервную копию рабочей базы.
2. Применить обновлённый `scripts/supabase/01-upgrade.sql` через Supabase SQL Editor **целиком**, либо `npm run db:migrate` с правильно настроенным серверным окружением. Не запускать `setup-db` на рабочей БД.
3. Выполнить `02-verify.sql` и `03-schema-audit.sql` / `npm run db:verify`; проверки должны быть OK.
4. Только затем выкладывать новую версию приложения. Обычный push кодовой ветки не применяет миграцию автоматически.
5. Проверить реальную загрузку файлов: нужны прежние Storage secrets и public uploads bucket. Ключи не передавать в браузер/чат.

Схема: 32 таблицы, 228 столбцов (с учётом новой админ-панели). `01-upgrade.sql` и schema audit регенерируются `npm run db:bundle`. В этой работе production БД/Storage не изменялись.

## Проверки

- `npm test`: валидатор, legacy moods, whitelist, фильтры очереди, регрессионные тесты проекта.
- `npm run test:suggestions`: реальные action/data routes с изолированной PGlite — 37 запросов, роли/приватность, все поля, лимит, legacy, idempotency, duplicates, принудительный rollback и SSE ревизия второго модератора.
- `npm run test:live`: в том числе отдельные upload kinds и user-scoped пути с fake Storage.
- `npm run test:wallet`: повторяемость 11 миграций, полный структурный audit и целостность кошелька.
- `npm run test:suggestions:browser`: настоящий production Next, локальный socket fixture, Chromium — заполнение формы, фильтры, четыре ширины 320/390/768/1280, правки/публикация/навигация, архив, отказ/Escape, история автора, параллельные повторы approval и семь одновременных заявок (принимаются пять). Требует окружение/необязательные браузерные инструменты по `docs/code-audit-2026-11-22.md`.
- `npm run test:routes`: общие HTTP-регрессии API.

Browser/HTTP suites изменяют только локальную marker-защищённую fixture, не production. Настоящий Supabase Storage и production deployment нужно отдельно проверить после выкладки.
