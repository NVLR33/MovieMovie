# Компактный интерфейс, SSE и изображения

## Интерфейс

- На главной компактнее превью вопроса дня и карточки сообщества. Короткие карточки
  не растягиваются до высоты самой длинной; четыре варианта ответа сохранены.
- В своём профиле категории: **Кинодневник / Кинопитомец и попкорн / Киновизитка /
  Титулы**. По умолчанию дневник. Студии монтируются только при выборе, а не занимают
  несколько экранов одновременно. Настройка оформления открывает дневник с редактором.
- Убрана обязательная минимальная высота пустых плиток дневника.
- Карточка фильма получает декоративный фон из backdrop, при его отсутствии — постера.
  Размывается сам фоновый слой (`filter: blur(40px)`), затем накладывается затемнение.
  `backdrop-filter` сам по себе не размывает установленную на тот же элемент картинку.
  Слой фиксированный, не перехватывает нажатия, не анимируется при скролле. На мобильном
  размытие/непрозрачность уменьшены; prefers-reduced-transparency/data отключают эффект
  в браузерах с поддержкой этих media features. При уходе с фильма фон удаляется.

## Топ по любимому

В полном топе и на главной есть третий критерий **По любимому** (`metric=favorites`).
Считается текущее число пользователей, добавивших материал в любимое, а не накопленная
история нажатий. Удаление из любимого уменьшает счётчик. Пары пользователь/материал
уникальны в БД; публичный каталог получает только агрегированные количества.
Материалы с нулём не входят в этот топ. При равенстве: рейтинг → число оценок →
просмотры → стабильный ID. Категории и ТОП-10/50/100 работают как раньше.
Изменения любимого инвалидируют публичный pulse через SSE.

## SSE без отдельного сервера

`GET /api/events` — стандартный Next.js Route Handler с Web ReadableStream.
**Runtime Node.js, не Edge:** существующий `pg` использует TCP/TLS Node и несовместим
с Edge. Отдельного WebSocket-процесса, брокера или платного realtime API нет.
Переход на настоящий Edge потребовал бы другого доступа к PostgreSQL и отдельной
проверки его транзакционной семантики; просто написать runtime=edge было бы ошибкой.

### Источник изменений

Девятая миграция `20261122-zz-realtime.sql` добавляет `mg_realtime_versions` и триггеры:

- сообщения/дружба — версии двух участников;
- уведомления — версия владельца;
- каталог — публичная версия;
- просмотры, оценки, комментарии, любимое, изменения пользователей — публичная и личная версии.

Хранится только номер аудитории и bigint-ревизия. Нет содержимого сообщений,
уведомлений, журнала событий или бесконечно растущей таблицы outbox.
Нулевая аудитория — публичная; личная берётся только из серверной сессии, не query string.
Изменение версии коммитится вместе с исходной записью. No-op UPDATE и откаты не
создают ложное изменение. Ревизия строки сериализуется под блокировкой: поздний
commit не теряется из-за более раннего sequence ID.

Один процесс приложения раз в 3 секунды читает маленькую таблицу одним пакетным
запросом для активных аудиторий. Не сканирует историю чата/каталог и не занимает
отдельное PG-соединение на каждого слушателя. Несколько экземпляров приложения
видят одну БД; in-memory EventEmitter не используется как единственный источник.
Номинальная задержка обнаружения — до 3 секунд плюс сеть/запрос и клиентское
объединение обновлений (около 0,9 с); это не zero-latency доставка.

### Доставка и безопасность

- Только события-инвалидации `pulse`, `chat`, `social`, без текстов и user ID.
- Чат и уведомления по-прежнему читаются через авторизованные REST API с проверкой
  дружбы; SSE не обходит эти проверки и не является каналом отправки сообщений.
- Одно EventSource-соединение на оболочку приложения, общее для открытых чатов.
  Старый таймер REST-запросов чата каждые 4 секунды удалён.
- При переподключении принудительный resync: пропущенные данные перечитываются,
  поэтому долговременное воспроизведение событий и Last-Event-ID не требуются.
- Heartbeat 15 с, срок потока 55 с, затем переподключение с повторной проверкой сессии.
  Автоматический retry 4 с, при лимите соединений 30 с. Ограничены медленные читатели,
  суммарное число соединений процесса (150), вкладки пользователя (8), гостевые (60).
- При скрытии вкладки соединение закрывается; при возвращении переподключение/resync.
  При отказе SSE резервное REST-обновление раз в 60 с, только для видимой вкладки.
  Это деградация, а не постоянный параллельный polling на исправном соединении.
- Публичный pulse обновляется через отдельный `/api/pulse` (каталог/рейтинг и SQL top-3),
  не загружая личные сообщения, уведомления и все пользовательские истории.
  Повторные инвалидации объединяются, изменения во время REST-запроса не теряются.
  Смена диалога отменяет старый запрос. В шапке есть небольшой индикатор соединения.
- Таблица ревизий с RLS, без доступа браузерных ролей. Триггер SECURITY DEFINER имеет
  фиксированный search_path и не принимает пользовательский SQL.

Ревизии — небольшая модель для текущего проекта, не обещание неограниченного масштаба:
публичная строка становится общей точкой сериализации записей. При высоком RPS
понадобятся нагрузочные замеры и шардирование/другой транспорт, не увеличение частоты опроса.

### Timeweb и reverse proxy

Ответ: `text/event-stream`, `Cache-Control: private, no-cache, no-store, no-transform`,
`X-Accel-Buffering: no`. Поток нельзя кэшировать или буферизовать на CDN/proxy.
Для собственного nginx location `/api/events`: `proxy_buffering off; proxy_cache off;`
и `proxy_read_timeout` больше heartbeat, например 75 с. Для управляемого Timeweb
проверьте фактическую доставку в DevTools → Network → events: фреймы должны приходить
до закрытия запроса. Если посредник игнорирует заголовок, настройте прокси/обратитесь
к хостингу. Проверка локальной реализации не доказывает настройки production-прокси.

## Мгновенный интерфейс с React 19

`useOptimistic` + async transition для **Буду смотреть / Любимое / Просмотрено /
Личная оценка**. Серверный снимок остаётся источником истины. Редьюсер чистый,
идемпотентный, поддерживает rebase поверх SSE-снимков и не выдумывает XP, попкорн,
достижения или глобальный рейтинг. Ответы до начала записи не перетирают её результат.

Ошибка записи завершает transition и откатывает только неподтверждённое представление;
успех сначала фиксирует локальное подтверждение, затем обновляет серверный снимок.
Повторные нажатия на одну операцию/материал блокируются до ответа, разные материалы
можно менять независимо. Для bookmark клиент отправляет явное желаемое `saved`,
сервер применяет его под блокировкой пользователя, а не безусловно переворачивает
состояние. Старый формат запроса без saved поддерживается для совместимости.

Это не offline-очередь: при неизвестном результате сетевого запроса данные нужно
перечитать. Создание материала остаётся подтверждаемым сервером действием — не
создаём фиктивный ID и кликабельную «успешную» карточку до проверки модераторских прав
и дубликатов на сервере.

## Изображения: URL в БД, файлы в Storage

`/api/upload` **уже использовал Supabase Storage** до этого изменения. Исправлены
обходы через `/api/action`, добавлены проверки magic bytes JPEG/PNG/WebP, границы 4 MiB,
неизменяемые случайные пути и длительный cache-control. Чужие постеры/фоны материалов
может загружать только администратор/модератор; аватар/шапка привязаны к владельцу.
MIME-проверка — проверка сигнатуры, не полноценный антивирус/декодер изображений.

API принимает для полей картинки только ограниченный HTTP(S) URL или локальный путь:
не data:, blob:, javascript:, не URL с логином/паролем. Девятая миграция дополнительно
ставит BEFORE-триггеры на users.avatar/header_image и movies.poster/backdrop:
новая inline-запись отклоняется и со стороны БД. Старые значения могут оставаться
**без изменений**, чтобы добавление просмотра/редактирование другого поля не ломалось.
Клиентские Base64-превью для экспорта киновизитки в БД не сохраняются и допустимы.
Оригинальный PNG-логотип не менялся.

### Перенос старых Base64

Сначала backup, настройте `uploads` по Supabase README и серверные env:
`MIGRATION_DATABASE_URL` (fallback DATABASE_URL), `NEXT_PUBLIC_SUPABASE_URL`,
`SUPABASE_SERVICE_ROLE_KEY`. Ключ только на сервере, не NEXT_PUBLIC и не в Git.

```sh
npm run images:migrate -- --dry-run # только количество/размер, без загрузок и UPDATE
npm run images:migrate -- --apply   # явное согласие на перенос
```

По одной записи за раз: строгий разбор Base64 → проверка размера/сигнатуры → upload
по стабильному пути с SHA-256 → compare-and-swap исходного поля на URL. Если upload
не удался, оригинал остаётся. Если пользователь уже сменил картинку, новая не
перезаписывается. Повторный запуск не переносит уже заменённые поля. Неподдерживаемые
форматы/oversize остаются без изменений с отчётом; нужны ручная конвертация и повтор.
Большие inline-строки не передаются из PostgreSQL в Node целиком. Секреты и содержимое
изображений не логируются. После прерванного переноса/конкурентного редактирования
возможно наличие невостребованного объекта в Storage; автоматическое удаление
старых файлов и VACUUM FULL намеренно не выполняются. Освобождение места на диске
PostgreSQL происходит не обязательно сразу после замены текста; используйте штатное
обслуживание БД, а не блокирующую очистку production без плана.

## Выкладка и проверки

Применить обновлённый **девятифайловый** `scripts/supabase/01-upgrade.sql`, затем
`02-verify.sql` и `03-schema-audit.sql`, затем приложение. Если SSE-таблица временно
недоступна, поток сообщает о деградации и закрывается, интерфейс использует резервное
обновление. Это не заменяет применение миграции.

```sh
npm test
npm run test:wallet
npm run test:live
npm run typecheck
npm run lint
npm run build
```

`test:live` проверяет настоящие API и триггеры в локальной PGlite, Storage подменяется
изолированным адаптером без внешней сети. Проверены права, отсутствие текста сообщений
в SSE, чужие аудитории, откаты/no-op, доставка инвалидирования, URL-only, неуспешные
загрузки и повторы bookmark. Браузерная проверка настоящей оболочки — ширины 320–1920,
переходы категорий, мгновенное добавление в список до ответа, rollback и успех,
объединение SSE-событий и отсутствие старого 4-секундного опроса чата.
Удалённая БД и настройки Timeweb этой сессией не изменялись.

### Повтор браузерного smoke-теста

`tests/integration/responsive-ui.mjs` запускает настоящие компоненты и CSS в Chromium,
но подменяет REST/SSE и Next-навигацию детерминированными фикстурами. Это не e2e
проверка production: маршруты/БД отдельно проверяет `test:live`. Скриншоты сохраняются
во временную директорию, путь печатается при запуске. Тест также проверяет оптимистичные
оценки (ошибка/успех) и то, что публичный pulse не вызывает `/api/data`.

Опциональные Linux-браузерные зависимости можно установить вне репозитория:

```sh
npm install --prefix /tmp/moviemovie-browser playwright-core@1.65.1 @sparticuz/chromium@153.0.0
UI_TEST_DEPS=/tmp/moviemovie-browser AWS_EXECUTION_ENV=AWS_Lambda_nodejs22.x \
  node tests/integration/responsive-ui.mjs
```

Для остальных окружений нужен совместимый Chromium; этот smoke-runner рассчитан
на Linux-бинарник `@sparticuz/chromium`, а не произвольную локальную ОС.
