# Supabase: обновление и автоматизация MovieMovie

Эти скрипты обновляют **существующую базу MovieMovie**, а не создают весь сайт с нуля.
Сначала сделайте резервную копию/снимок базы. Запускайте от владельца таблиц
(в Supabase обычно `postgres`). Схему обновляйте **до** выкладки новой версии приложения.

## Вариант 1 — SQL Editor (без локального запуска)

1. Откройте нужный проект Supabase → **SQL Editor → New query**.
2. Скопируйте **весь** файл [`01-upgrade.sql`](01-upgrade.sql), выполните **Run**.
3. Выполните [`02-verify.sql`](02-verify.sql) и [`03-schema-audit.sql`](03-schema-audit.sql): у каждой проверки должно быть **OK**.
4. Если используете загрузку изображений, выполните отдельно [`04-storage-setup.sql`](04-storage-setup.sql).
5. Выкладывайте приложение. В редакторе материалов заполните актёров, франшизы
   и фестивальные отметки. Эти сведения не подставляются автоматически и не выдумываются.

`01-upgrade.sql` собирается из всех файлов `scripts/migrations/*.sql`. Он:
- добавляет актёрский состав, метаданные фильмов, теги спойлеров и выбранный титул;
- добавляет структуру сезонов/эпизодов, отдельные оценки, постоянные завершения сериалов и журнал первых зрителей;
- добавляет питомцев и журнал попкорна с baseline исторических активностей (шестая миграция);
- сохраняет дробную выработку проектора (седьмая миграция), не меняя старые балансы;
- создаёт журналы скрытых трофеев и постоянных титулов с уникальными индексами;
- сохраняет заслуженные зрительские ранги по существующим просмотрам;
- включает RLS и убирает права `anon`/`authenticated` на новые таблицы наград и их sequences;
- фиксирует SHA-256 миграций в отдельной схеме `moviemovie_migrations`;
- добавляет восемь индексов для существующих систем (восьмая миграция);
- добавляет полную карточку предложений, индексы очереди и защищённую историю модерации (десятая миграция);
- сверяет всю схему по Drizzle-контракту перед COMMIT и останавливается при несовместимости;
- выполняется в одной транзакции, без DROP/TRUNCATE и очистки пользовательских данных.

SQL Editor и CLI пропускают применённые файлы по имени и хешу, а не исполняют backfill снова.
Повторный запуск безопасен. При ошибке транзакция откатится; если редактор оставил
сессию в состоянии aborted transaction, выполните `ROLLBACK;` перед повтором.
Конкурирующие запуски сериализуются advisory-lock; ожидание блокировки ограничено 15 с,
отдельного SQL-оператора — 120 с. Для большой базы заранее оцените backfill на staging.

## Вариант 2 — команда миграции (локально или на CI)

```sh
npm ci
npm run db:migrate -- --dry-run # список локальных файлов и хешей; к БД не подключается
npm run db:status              # только чтение: какие миграции применены/ожидают
npm run db:migrate             # применить отсутствующие и проверить схему до COMMIT
npm run db:verify              # все проверки отдельно, в read-only транзакции
```

В `.env` или secret-хранилище окружения задайте **MIGRATION_DATABASE_URL** — строку
PostgreSQL из Supabase **Connect**, с SSL-параметрами, рекомендованными Supabase.
Предпочтительно Direct connection или Session pooler (обычно порт 5432).
Это не project API URL, не anon key и не service-role API key. Если переменная пуста,
используется существующая `DATABASE_URL` — перед запуском проверьте, что это нужная БД.
Никогда не передавайте пароль в чат/репозиторий и не используйте префикс `NEXT_PUBLIC_`.

Команда удерживает одну транзакцию и advisory-lock на весь пакет: ошибка откатывает
весь запуск. Успешные файлы учитываются по имени и хешу. Редактирование уже применённого
файла обнаруживается и блокирует запуск: для дальнейших изменений добавляйте новый SQL.
SQL Editor и CLI используют один журнал. Не запускайте `drizzle-kit push` автоматически
против production: он сравнивает всю схему; эти миграции ограничены явно заданными изменениями.

## Вариант 3 — ручной запуск из GitHub Actions

В репозитории есть workflow **Apply Supabase migrations**:

1. После попадания workflow в default branch создайте GitHub Environment **production**.
2. Добавьте в нём environment secret **SUPABASE_DB_URL** с PostgreSQL connection string.
3. Рекомендуется включить required reviewers и ограничить deployment branches.
4. Откройте **Actions → Apply Supabase migrations → Run workflow**, выберите проверенную
   ветку/версию и подтвердите запуск. Перед выкладкой убедитесь, что job завершился успешно.

Workflow сначала запускает unit/integration-тесты без удалённой БД, затем миграции,
полную проверку схемы и отчёт статуса. Workflow не запускается от обычного push/PR. Он не выполняет код из pull_request_target,
не печатает connection string и не применяет миграции к какой-либо БД без настроенного secret.
В этой сессии удалённая база не менялась; workflow не запускался.

## Безопасность и границы

Новые таблицы наград доступны доверенному серверному подключению, а не браузерным
ролям Supabase Data API. Next.js должен подключаться владельцем этих таблиц или
специально настроенной серверной ролью с необходимыми правами/BYPASSRLS. Существующие
RLS-политики остальных таблиц не изменяются. Это не полный аудит безопасности всей базы.

Для пустой БД сначала задайте серверную `DATABASE_URL` и используйте
`npx tsx scripts/setup-db.ts` (создание текущей схемы через Drizzle), затем этот набор миграций. На production не запускайте setup-db вместо upgrade.
Чтобы пересобрать единый SQL после добавления будущих миграций: `npm run db:bundle`.
Сгенерированный SQL включается в Git, чтобы SQL Editor и CLI всегда видели одинаковый пакет.


## Обновление достижений: сезоны, эпизоды и «Первопроходец»

Новая миграция — `20261122-series-achievements.sql`. Порядок прежний: backup →
`01-upgrade.sql` → `02-verify.sql` → выкладка приложения. Старые файлы миграций
не изменялись. Повторный запуск пакета сохраняет оценки и заслуженные награды.

В карточке сериала администратору/модератору доступен редактор сезонов и эпизодов.
Старое общее число серий **не** преобразуется в выдуманную структуру.
Редактор вводит реальные сезоны, количество эпизодов и при желании их названия,
затем подтверждает полный список. Оценки сезонов и эпизодов сохраняются отдельно от
общей оценки сериала, без дополнительного XP. Ачивка требует минимум 10 эпизодов.
Изменение структуры снимает подтверждение, но уже засчитанный сериал не отбирает.
Подробнее: [`docs/achievements.md`](../../docs/achievements.md).

«Первопроходец» не выдаётся задним числом: существующие просмотры и журнал скрытых
событий помечают материал как уже открытый. Для ещё не просмотренного фильма первый
новый просмотр фиксирует владельца под блокировкой фильма. Оценка и отдельный отзыв
от 80 символов после открытия завершают условие в любом порядке. Просмотры, удалённые
до появления журналов, восстановить невозможно; такие исторические данные не угадываются.
Ни один из этих скриптов сам по себе не подключается к рабочей базе при обычном пуше.


## Кино-Эволюция и карта мира

Шестая миграция `20261122-virtual-pet.sql` создаёт `mg_cinema_pets` и
`mg_popcorn_ledger`, уникальные источники наград, проверки кошелька, RLS и запреты

## Обновление кошелька попкорна

Седьмая миграция — `20261122-wallet-economy.sql`. Добавляется только
`production_carry` с ограничением диапазона: дробный остаток выработки. Никакого
пересчёта старых балансов, цен и покупок нет. Недельные задания и разовые рубежи
используют уже существующий журнал с уникальными источниками.

Текущий `01-upgrade.sql` содержит **девять** миграций; ранее применённые
файлы пропускаются по журналу и хешу. После применения запустите `02-verify.sql`.
Если первые шесть миграций уже установлены, будут применены седьмая и восьмая.

Проверка экономики без удалённой БД: `npm ci && npm run test:wallet`. Тест
запускает настоящие API-обработчики на изолированной PGlite, а не на `DATABASE_URL`.

## Итоговая проверка всех систем

Контракт `03-schema-audit.sql` генерируется из **всех 32 таблиц / 228 столбцов**
`src/db/schema.ts`, включая базовые системы. Проверяются типы, nullable/NOT NULL,
наличие обязательного DEFAULT, PK/unique/FK и действия удаления, валидность и состав
индексов, именованные CHECK и требуемый RLS. Дополнительные пользовательские поля
не удаляются. Значения DEFAULT, содержимое CHECK и все пользовательские RLS-политики
на семантическую эквивалентность не сравниваются: это структурная готовность, не
универсальный аудит безопасности или качества данных.

Если старая база отличается от базовой схемы (нет старой таблицы/поля, неверный тип),
выполните `03-schema-audit.sql` отдельно и сохраните названия проверок со статусом
NEEDS ATTENTION. Пакет намеренно не угадывает пропущенные email, пользователей,
просмотры, сезоны и страны и не удаляет дубли для создания ограничений. Потребуется
отдельная адресная миграция под фактический отчёт; автоматический откат не исправляет
несовместимость, которая существовала ещё до запуска.

Восьмая миграция `20261122-z-system-indexes.sql` не изменяет данные и уникальность.
Используется обычный CREATE INDEX внутри транзакции, **не CONCURRENTLY**: на большой
базе запланируйте окно обслуживания и предварительный прогон на staging. Таймаут
прервёт и откатит пакет, а не оставит частично применённые миграции. Это индексы
доступа, не обещание ускорить любые запросы без EXPLAIN/нагрузочного теста.

### Изображения и Supabase Storage

`04-storage-setup.sql` — отдельный необязательный шаг, не обычная PostgreSQL-миграция.
Создаёт отсутствующий `uploads`: публичное чтение, 4 MiB, JPEG/PNG/WebP. Файлы,
storage.objects и write-политики не трогает: загрузка идёт через серверный
SUPABASE_SERVICE_ROLE_KEY после проверок пользователя. При несовпадении настроек
существующего бакета выдаёт ошибку и **не делает приватный бакет публичным**.
Не запускайте этот файл, если в вашем проекте намеренно другая модель хранения.
Альтернатива — `npx tsx scripts/setup-storage.ts` с серверными env-переменными;
он также сверяет настройки, а не объявляет любой существующий бакет готовым.

Матрица всех систем и границы проверки: [docs/database-systems-audit.md](../../docs/database-systems-audit.md).


## Живые обновления и URL-only изображения

Девятая миграция `20261122-zz-realtime.sql` добавляет одну приватную таблицу
ревизий и триггеры для SSE, а также запрещает новые inline-записи в поля картинок.
Старые Base64 остаются неизменными до явного переноса. Повторный запуск прежние
файлы пропускает по хешам. После миграции должны пройти новые проверки SSE и image guards
в `02-verify.sql` и контракт 32 таблиц в `03-schema-audit.sql`.

`npm run images:migrate -- --dry-run` показывает объём старых inline-картинок;
`--apply` явно включает загрузку в Storage и замену только успешно перенесённых
значений на URL. Это отдельное обслуживание с backup, не автоматическая часть
SQL-миграции и не причина переписывать все URL каталога.

SSE использует Node.js Route Handler и обычный HTTP streaming, не Edge (pg требует
Node) и не отдельный WebSocket-сервер. На прокси нельзя буферизовать `/api/events`.
Детали, проверки и Timeweb: [docs/live-ui-storage.md](../../docs/live-ui-storage.md).
